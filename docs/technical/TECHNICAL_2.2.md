# 空间文件夹 2.2：文件安全与撤销技术说明

## 设计目标

2.2 不把画布变成独立文件系统。真实文件仍是唯一真相源；新增层只记录“哪些真实变更已经发生，如何安全地反向执行”。

## 数据结构

- `OperationRecord`：操作类型、状态、时间、用户可读摘要、可逆文件动作和画布元数据。
- `ReversibleFileAction`：路径迁移、新生项目、移除项目和 Finder 标签变更。
- `OperationHistoryStore`：每个根文件夹一份 JSON 日志，使用原子写入，最多保留 200 条。
- `FileOperationEngine`：在 `applied` 和 `undone` 之间执行可逆迁移，并处理同名冲突。

## 状态规则

1. 真实文件修改前，先持久化 `pending` 记录。
2. 文件系统操作完成后更新为 `applied`。
3. 撤销后为 `undone`，重做后回到 `applied`。
4. 新操作发生时，旧的重做分支标记为 `superseded`。
5. 重启后遇到 `pending` 记录，标记为 `unavailable`并要求用户在 Finder 核对。
6. 布局快照不跨重启；对应历史会标记为 `viewOnly`。

## 覆盖为何可逆

“替换”不使用直接覆写。旧项目先进入废纸篓，新项目再进入目标路径。撤销时按相反顺序执行：先移开新项目，再恢复旧项目。恢复过程如再次遇到冲突，仍必须由用户选择。

## 数据安全防线

- 操作前预检所有源路径，避免多项撤销做到一半才发现缺少文件。
- 同名项目默认不覆盖。
- 损坏日志不会被静默覆写；真实文件修改会暂停，原日志可存档到 `Operations/Corrupt`。
- 根文件夹移动后，画布内部路径会按新根目录迁移，外部导入源路径保持不变。
- 诊断报告只包含版本、屏幕/画布尺寸、项目数量、操作类型/状态和错误类别。

## 仍然存在的边界

- 外部 App 在操作后再次移动或删除目标时，无法无损推断其新位置；引擎会停止而不是猜测。
- 系统崩溃可能发生在文件系统调用与日志状态更新之间的极短窗口；重启后会将该操作标记为需核对，不会自动继续。
- 当前未处理多设备同时编辑 iCloud 画布日志的合并冲突。
